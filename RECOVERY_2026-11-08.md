## 4. Hard rules (why this happened, and the guardrail for each)

These are non-negotiable. A session that cannot satisfy a rule stops and asks.

- **R1 — Never commit a binary you did not build in this session.**
  `src/jutsu/_jutsu.so` is derived from `crates/jutsu-core/`. If you change any
  Rust source, rebuild it (`cargo build --release -p jutsu-core && cp
  target/release/lib_jutsu.so src/jutsu/_jutsu.so`) *and* re-run the full Python
  suite before committing. A `.so` that does not correspond to the committed
  Rust source is a landmine: it was exactly how `47821c6` silently broke three
green tests. If you cannot rebuild (no toolchain), commit *source only* and say
  so — never ship a stale or hand-edited `.so`.

- **R2 — Build from source, always.** The committed `.so` must be reproducible
  from the committed Rust sources in this tree. Treat `src/jutsu/_jutsu.so` as a
cache artifact, not as an input you edit.

- **R3 — A test file is a claim; it must pass before it is added.** Never write
  or commit a test that asserts behaviour you have not *observed* by running it.
  The invented `test_*_rust.py` / `test_ext_thirdparty_enhanced.py` files asserted
  false facts (`BaseLoader` abstract, `Extension.filters`, native-env string
  results) and turned a green suite red. If a test fails on first run, the *code
  or the assertion* is wrong — fix it or delete it; do not commit it as "done".

- **R4 — Read a file before you edit it; never prepend/append blindly.** The
  `lib.rs` break came from prepending a duplicate module preamble to a file that
  already had one. Before editing any existing file, open it and confirm the
  structure (for Rust: balanced braces / one crate root). After editing Rust,
  `cargo build` must succeed *before* you commit.

- **R5 — Never delete or summarise-away the living docs.** `STATUS.md`,
  `TODO.md` and the `PLAN_*.md` files are the plan of record. They may be
  *updated with measured facts*, never replaced by a vague "everything is done"
  summary. If you change scope, edit the relevant `PLAN_*`/`TODO` entry in place
  and keep the numbers current.

- **R6 — "Done" requires evidence.** A completion claim is only valid if it
  cites a fresh run of all three suites (Rust, Python, JS) with exact pass/fail
  counts. No `FINAL_*_REPORT.md` / "all phases complete" document may exist
  unless every number in it was produced by a command you ran this session.
  If in doubt, the honest answer is "not done; here is what still fails."

- **R7 — One concern per commit; name it accurately.** The corrupted history is
  full of commits named "refactored for publishing" / "got C done" that actually
  mangled unrelated files. Commit message must describe the *actual* diff, and a
  commit must not mix a source change with an unrelated doc rewrite or a binary.

- **R8 — Verify before you flip defaults or wire new paths.** New engine paths
  (e.g. `JUTSU_RUST_EVAL`) stay default-off until their exit criteria in the
  relevant `PLAN_*` are met and green. Do not let an "in progress" slice look
  finished.
